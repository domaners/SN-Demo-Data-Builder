# Installing and using Demo Data Builder (Phase 1)

Phase 1 covers the provider layer, scenarios, blueprint generation and validation, the record ledger,
foundation data (companies, locations, departments, cost centers, users, groups, roles), the setup
check and reset. CMDB, service maps, ITSM tasks and the lifecycle scheduler come in later phases.

> **Status:** the update set is generated by `build/build.js` and checked by the test suite, but it has
> not yet been committed on a live instance. Install it on a throwaway PDI first and report anything
> the preview step flags.

## 1. Install the update set

1. Download `dist/ddb-0.1.0.xml` from this repository.
2. On the PDI, as `admin`: **System Update Sets > Retrieved Update Sets > Import Update Set from XML**,
   upload the file.
3. Open **Demo Data Builder 0.1.0**, click **Preview Update Set**, resolve anything listed (there
   should be nothing on a clean instance), then **Commit Update Set**.
4. Refresh the browser. The **Demo Data Builder** application menu appears.

The app installs in its own scope (`x_ddb`). It is blocked on any instance with
`glide.installation.production = true`. To restrict it further, set `x_ddb.allowed_instances` to a
comma-separated list of instance names.

## 2. Give it a Claude API key

The recommended way is a Connection & Credential alias, so the key never sits on an app table.

1. Switch the application picker to **Demo Data Builder**, then **Connections & Credentials >
   Connection & Credential Aliases > New**: Name `anthropic`, Type `Credential`. Its ID becomes
   `x_ddb.anthropic`. (If you create it in another scope, put that alias's ID in the provider config.)
2. **Connections & Credentials > Credentials > New > API Key Credentials**: give it a name, paste the
   Anthropic API key, and set **Credential alias** to the alias above.
3. **Demo Data Builder > Providers > New**:

   | Field | Value |
   |---|---|
   | Name | Claude |
   | Provider | Anthropic API |
   | Purpose | Any |
   | Model | `claude-opus-5-5` (default) |
   | Effort | Medium |
   | Credential alias | `x_ddb.anthropic` |

   Prices default to Claude Opus 5.5's list prices and only feed the cost estimates. The daily token
   budget defaults to 2,000,000 tokens per provider config; 0 means unlimited.

If you can't create aliases, leave **Credential alias** empty and put the key in **API key
(fallback)**, an encrypted field.

## 3. Run the setup check

**Demo Data Builder > Setup Check**, then **Test connection**. The connection test calls
`GET /v1/models/{model}` and uses no tokens. Fix anything marked *Problem*.

If *Outbound HTTP timeout* warns, raise `glide.http.outbound.max_timeout` (seconds) or lower the
effort; each blueprint section is one synchronous call.

## 4. Create a scenario and a blueprint

1. **Demo Data Builder > Scenarios > New**: industry (free text, e.g. "Regional hospital group"),
   optional company name, size (Small 200, Medium 1,000, Large 5,000 people, or a custom headcount),
   regions, and any extra instructions. Leave **Seed** empty to get a random one.
2. Click **Generate Blueprint with Claude**. You land on the job record; refresh to see progress. Four
   calls are made, one per section (organisation, people and groups, applications, infrastructure and
   catalog), followed by validation.
   - Or click **Load Example Blueprint** to use the bundled *Halden Freight Logistics* blueprint with
     no LLM call.
3. Open the blueprint. Read the **Summary**, check **Validation warnings**, and edit **Blueprint JSON**
   if you want (an edit sets it back to Draft; click **Validate**).
   - If it is **Invalid**, click **Repair with Claude** to regenerate just the sections the errors
     point at, or fix the JSON by hand.
4. Click **Preview Build** to see record counts, then **Approve**.

## 5. Build the foundation data

On the approved blueprint click **Build Foundation Data**. The job writes records in steps of
`x_ddb.max_records_per_step` (default 200):

1. Company, cost centers, locations (hierarchy, time zones), departments (heads, cost centers).
2. The simulated directory (**Directory Users**, **Directory Groups**): objects shaped like Active
   Directory entries, with DNs, objectGUIDs, managers and group membership.
3. A directory sync into `sys_user` and `sys_user_group`: users coalesce on objectGUID and carry
   `source = ldap:<DN>`; managers, departments, locations, cost centers, group memberships and roles are
   set. Simulated users have notifications disabled and `.example` email addresses.

Every record is listed in **Record Ledger**. Building the same approved blueprint again updates the
same records instead of creating duplicates.

## 6. Reset

- **Reset Scenario Data** on a scenario deletes everything DDB created for it.
- **Reset Data From This Job** on a build job deletes only what that build created.

Records DDB did not create are never touched.

## Jobs, retries and costs

- Jobs run in the background (event `x_ddb.job.step`, Script Action **DDB Job Step**).
- **DDB Job Watchdog** runs every minute: it retries jobs waiting after a rate limit or overload
  (backoff 30 s, 60 s, 120 s, 240 s; four attempts) and re-queues steps that stalled.
- **Cancel Job** and **Retry Job** are on the job form. A retried job resumes where it stopped.
- **LLM Calls** lists every request: model, tokens, cache hits, latency, stop reason, estimated cost.
  The API key and request headers are never stored.

## Roles

| Role | Can |
|---|---|
| `x_ddb.admin` | Everything: providers, prompts, scenarios, blueprints, builds, resets |
| `x_ddb.user` | Read scenarios, blueprints, jobs, directory objects and the ledger |

Platform admins keep access through `admin_overrides`.

## Uninstalling

Reset each scenario first (so the users, groups and locations are removed), then back out the update
set or delete the Demo Data Builder application record.
